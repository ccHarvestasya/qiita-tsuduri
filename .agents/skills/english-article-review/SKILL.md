# English Article Review

海外向け英語原稿の **独立した公開前レビュー** を担当する。単なる翻訳の校正やAIらしい表現の機械的な削除ではなく、想定読者が内容を正確に理解し、必要なら再現・判断できるかを確認する。

**文体の比較対象:** [生原稿由来の著者の文体プロファイル](../../../docs/author-voice-profile.md)を参照する。英語を自然に直しても、著者の問い・実験の動機・発見・適切な留保を削らない。日本語の軽口を直訳することも、画一的な英語へ均質化することも要求しない。曖昧さや不正確さは根拠を付けて指摘する。

## 適用範囲と前提

作業開始時に次を確認する。

1. リポジトリの `AGENTS.md`
2. [共通編集方針](../../../docs/editorial-policy.md)
3. [制作・レビュー手順](../../../docs/article-workflow.md)（4観点、独立性、重大度、PASS/REVISE）
4. [海外向けコンテンツ運用](../../../docs/overseas-content-workflow.md)
5. 対象のDraft PR／ブランチ、`content.yaml`、その `manuscripts.en.file` が示す英語正本、`REVIEW.md`、関連する既存記事と一次資料

- **主対象**: Substack・Medium・Payhip向け英語無料稿。初出順は指定と管理情報に従う。技術記事、解説、エッセイのいずれにも適用する。
- **有料原稿**: 有料記事は [english-paid-article-review](../english-paid-article-review/SKILL.md)、有料書籍は [english-paid-book-review](../english-paid-book-review/SKILL.md) を使う。言語品質も各専用スキルが担当する。
- **対象外**: 新規原稿の執筆、全面改稿、価格・販売設定、投稿、公開、PRマージ。レビュー中は原則として本文を編集しない。修正依頼が明示された場合も、指摘と修正結果を区別する。
- **言語**: 公開本文・購入者向け素材は英語。レビュー結果、`REVIEW.md`、検証記録、PR文面は日本語。実行コマンド・ログ・固有名詞は原文を保持する。

## 1. 対象と正本を確定する

1. 対象の媒体、読者像、記事が答える問い、読後に理解・実行・判断できることを把握する。単に「海外一般」とせず、前提知識と対象環境を原稿から特定する。
2. `main` だけを根拠にせず対象Draft PRのheadを読み、`content.yaml` の `manuscripts.en.file` と原稿の実体を照合する。旧形式のPRでは `source_file` を確認する。旧 `overseas/` など従来配置の原稿は存在・公開状態を確認し、無断で移動しない。
3. `REVIEW.md` で既存の指摘、実機検証結果と未検証項目を確認するが、著者の「確認済み」を独立した検証の証拠にしない。
4. 日本語原稿から英語化した場合、参照可能な原文と比較して主張、例外条件、因果関係、独自の視点の脱落・改変を確認する。元記事を前提にせず、英語記事単独で成立することも確認する。
5. 同一本文の再掲載でも二重管理しない。再掲載をレビューする場合は英語正本、元の公開URL、Import/canonicalの手順・状態を確認し、未公開URLを捏造しない。

## 2. 技術的正確性と再現性

共通の独立レビュー基準に従い、結論に関わる主張から優先して公式資料、標準、原実装などの一次情報を確認する。

- **事実の種類**: 仕様上の保証、特定バージョン／環境での観測、解釈・意見、将来予測を区別する。日付・製品の現行仕様・価格等は確認時点と出典を残す。
- **手順の成立性**: OS・リリース・シェル・権限・前提パッケージ・操作場所・入力値が明示されているか。コマンド／設定／出力／判定方法が本文と一致するか。可能なら隔離された安全な環境で追試し、実施条件・実際の結果を記録する。
- **危険操作**: SSH設定、UFW、IPv4/IPv6、クラウドFW、再起動、削除、権限変更等について、リモートアクセス喪失・既存接続への影響・復旧経路を **該当操作より前** に説明しているか。環境依存の条件を普遍化していないか。
- **比較と結論**: 製品・プロトコル・暗号方式などを根拠なく優劣断定しない。Symbol／NEMなど固有仕様は混同しない。記事の主要な結論を支える資料が不足する場合は `Unverified` とする。
- **未実施の扱い**: 著者が追試済みでも本レビュー担当が未追試ならその事実を区別する。実行できないテストをPASSと記載せず、実測出力や引用を創作しない。危険・課金・秘密情報の伴う操作を確認のために勝手に実行しない。

エッセイでは実機検証を機械的に要求しないが、歴史・統計・AIの能力・制度等に関する具体的な事実と、著者の哲学・意見を区別して検証する。

## 3. 英語圏向けの文章・読者体験

以下は **品質確認の観点** であり、機械的な禁止語リストや米国英語への一律統一ではない。

- **英語の自然さ**: 日本語の語順や直訳で不自然になっていないか。動作主体・因果・条件・代名詞の指示対象が明確か。技術者に通用する用語を使い、過度に日常語へ置換して技術的意味を壊していないか。
- **AI的な画一化**: 内容を進めない大げさな導入、抽象的な賛辞、連続する紋切り型のつなぎ句、結論の言い換え反復を点検する。ただし特定の単語だけを理由に減点せず、文脈と読者への実害で判断する。
- **著者の声**: 経験、発見、疑問、反例、独自の判断やユーモアを無断で均質化しない。客観的事実と個人的見解を適切に示し、エッセイを不必要に教科書調へ変えない。
- **論理と長さ**: 段落間で問いから結論へ自然に進むか。定義・比喩・実例が理解を前進させるか。長さ自体を問題にせず、短縮によって根拠、背景、例外条件、復旧方法、筆者の意図を失わせない。
- **地域・文化前提**: 日本固有の習慣、サービス、法律、料金、商習慣、ネットワーク環境を国際共通の前提にしていないか。英米差、クラウド事業者差、OS差、単位や日付表記は **意味が変わる場合** に明示する。不要なローカライズは強制しない。
- **読み物としての完成度**: タイトルは本文の約束に合い、結論を不自然に先延ばしにせず、説明・具体例・留保が読者の理解を支えるか。SEOや販売文句を優先して正確性・著者の視点を損ねない。

英語力を「ネイティブ保証」や「AI検出率」で測定しない。変更提案には問題箇所を短く引用し、誤解される理由と必要に応じた自然な英文例を示す。単なる好みの差をMajorにしない。

## 日本語レビュー版がある場合の自然さ確認

日本語の `article.ja.md` などが添えられている場合、英語正本との意味・条件・手順の一致だけでなく、**日本語だけを通して読んだ自然さ**を独立に確認する。[文体プロファイルの具体例](../../../docs/author-voice-profile.md)に照らし、次を検査する。

- 英文の語順を引きずる不自然な主語・述語・接続や、架空の読者心理がないか。
- 「ここにも気を付けたい」「理由があります」などの情報のないメタ説明が、技術的な内容を薄めていないか。
- コード間の説明に無理な話題転換がなく、なぜ操作するのかが日本語で自然につながるか。
- 重大な意味の欠落は技術・内容の指摘とし、読みづらさは実際の文章を短く示して具体的に指摘する。**文法が正しいだけで文章品質をPASSとしない。**
- 日本語稿の不自然さが多く、著者が確認に使えない水準なら改稿が必要と記録する。英語原稿の独立レビュー判定とは対象・根拠を区別する。

## 4. 媒体・無料／有料の境界

- Substackの無料記事は、一つの問いに対して独立して読める完成した内容とする。必要な結論・注意点・最小再現を有料版への誘導のために隠さない。
- Payhip等の未公開有料原稿、配布コード、独自のノウハウを無料原稿、公開レビュー、PR本文に転載しない。重複の確認は必要最小限に限定する。
- Medium再掲載時には `PUBLISHING.md` と実際の正本URLを照合し、canonical/importが未実施なら未実施として扱う。本文のコピー作成をレビュー結果として提案しない。
- 説明文、リンク、引用、画像・コードの再利用条件について、確認できる範囲を区別する。表示・リンク検証をしていなければ確認済みにしない。
- 無料／有料の範囲、読者の安全、情報の正確性は公開先の都合より優先する。クリック率・売上予測はPASS/REVISEの根拠にしない。

## 5. 判定と記録

判定・重大度は [制作・レビュー手順](../../../docs/article-workflow.md) の **Critical / Major / Minor、PASS / REVISE** に従う。

- **Critical**: 重大な危険操作や秘密情報・資産に関する誤案内、未公開有料資産の漏えい等。
- **Major**: 核心の誤り、実行不能な主要手順、必須の復旧条件欠落、英語の曖昧さにより中心結論を誤読させる構成、核心の未検証等。
- **Minor**: 局所的な語法・用語不一致、冗長さ、表記揺れ、影響が軽微な地域表現等。
- **PASS**: Critical・Majorがなく、公開を妨げる核心の未検証がない。Minorが残っていてもよい。
- **REVISE**: Critical・Majorがある、または核心を確認できず正確性を判定できない。好みの校正だけでREVISEにしない。

レビュー結果と追試記録は対象の `REVIEW.md` に **日本語で** 記録する。既存の実測欄・指摘履歴を壊さず、原稿の対象ブランチ／commit／確認日、確認方法、実行環境、結果、未確認事項を追跡できるようにする。既存フォーマットがあればそれを優先する。報告の基本形は以下。

```markdown
# Review Result
判定: REVISE
対象: contents/free/draft/<日本語タイトル>/article.en.md
対象版: <commit または特定可能な版>
レビューの独立性: <執筆と別の担当・コンテキストか、自己レビューか>

## Major
- [EAR-001] 対象の見出し／行
  - 問題:
  - 読者への影響:
  - 根拠:
  - 最小修正案（必要なら英語例）:

## Verified
- 技術・再現性:
- 英語・構成・著者の視点:
- 海外読者の前提と無料／有料の境界:
- 確認した一次資料、実行したコマンド／実際の結果（ある場合）:

## Unverified
- 未確認事項・理由・公開判定への影響:
```

Critical／Minorも同じ形式で必要なときだけ追加し、指摘IDは `EAR-001` から連番にする。再レビュー時は同じ問題に同じIDを使い、解消・未解消・新規の区別を記録する。

**独立性を偽らない**: 原稿作成者が同じコンテキストで読み直しただけなら自己レビューであり、`independent_review` を完了にしない。独立したレビューを実施したことを確認できる場合のみ、その根拠を記録する。

`content.yaml` の `status`、`verification`、`publication`、`sales` は別々の状態とする。PASSだけで原稿を公開済みにせず、管理値を証拠なしに更新しない。レビュー後も投稿、販売、マージ、公開用アセット生成は行わない。

## 完了条件

- 対象の正本・版・読者像が特定されている。
- 中心主張の出典・実行結果／未検証の境界が説明できる。
- 英語の自然さ、論理、著者の独自性、国際的な前提を点検し、指摘の根拠が示されている。
- 無料／有料と公開状態を混同せず、非公開素材を漏らしていない。
- 日本語の判定・指摘・未確認事項が追跡可能で、独立性を過大に主張していない。

## 日本語の直訳・慣用表現の検査

[翻訳表現のレビュー基準](../../../docs/english-translation-review.md)を必ず適用する。日本語の慣用句・比喩・ことわざ・決まり文句・婉曲表現・主語省略を語句の対応だけで訳していないか確認する。文法が正しいだけでは合格にしない。原文の意味・語調・条件を保ち、文脈に合った自然な英語かを英語稿単独でも通読する。

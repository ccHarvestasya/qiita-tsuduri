# English Article

日本語無料記事を英語へ翻訳・展開する Skill。翻訳、技術解説、実務手順、エッセイを扱う。日本の著者による経験や疑問、技術的な深さを残しながら、英語圏の読者が単独で理解・判断・再現できる記事を作る。

日本語原稿からの文体継承には[生原稿由来の著者の文体プロファイル](../../../docs/author-voice-profile.md)を使う。語尾や日本語の軽口を直訳せず、問い・実験の動機・試行錯誤・発見・留保・情報量を、自然で真面目な英語の文章として残す。著者にない経験・ジョークを創作しない。

## 翻訳の担当

日本語原稿から自然な英語への翻訳は本スキルが担当する。[英語翻訳の共通手順](../../../docs/english-translation.md)を適用し、英語として単独で通読した自然さと、日本語原稿との意味・条件・情報量の一致を両方確認する。日本語稿の制作・修正が必要な場合は対応する日本語制作スキルへ引き渡す。

## 制作経路

[日本語執筆から英語翻訳まで](../article-workflow/SKILL.md)に従う。翻訳元は `manuscripts.ja.file` の日本語無料稿で、原稿がなければ日本語稿を先に整える。対象はSubstack・Medium・Payhipで、初出順を固定しない。既存英語稿の改稿はその稿を対象とする。翻訳元の版と変更理由を `REVIEW.md` に記録する。

## 作業開始と責務

最初に、対象に必要な範囲で以下を読む。

1. リポジトリの `AGENTS.md` と対象記事・Draft PRブランチ
2. [共通編集方針](../../../docs/editorial-policy.md)
3. [制作・レビュー手順](../../../docs/article-workflow.md)
4. [海外向けコンテンツ管理](../../../docs/overseas-content-workflow.md)
5. 対象の `content.yaml`、`article.en.md`、`REVIEW.md`、関連原稿、実機検証記録、一次情報

- **担当**: 新規記事の企画・執筆、既存英語記事の改稿、既存日本語原稿の英語圏向け再構成、自己レビュー、必要な制作・検証記録の作成。
- **担当しない**: 独立した公開前判定、Payhipの有料教材作成、Substack/Mediumの投稿、商品登録、PRのマージ、公開状態の確定。独立レビューは `english-article-review` に引き継ぎ、同一コンテキストの自己点検を独立レビューとして記録しない。
- **言語**: 公開する `article.en.md` は英語。著者用の `REVIEW.md`、調査・検証メモ、`PUBLISHING.md`、PRタイトル・本文は日本語。コマンド・コード・設定キー・ログは原文を維持する。
- **対象媒体**: Substack・Medium・Payhip向けの無料稿。同一本文は媒体別に複製しない。

## 1. 対象・既存資産・保存先を確定する

1. 依頼で指定された題材、読者、伝えたい主張、必要な詳しさ、改稿範囲を優先する。決まっていない細部は既存シリーズと原稿から判断し、執筆前の質問を増やさない。
2. `main` だけでなく関連するDraft PR・未マージ記事・公開済み記事も探し、同じ論点の原稿を不用意に二重作成しない。
3. 新規の英語無料記事は原則として `contents/free/draft/<日本語記事タイトル>/` に置き、`article.en.md`（英語正本）、`content.yaml`（状態管理）、`REVIEW.md`（日本語の調査・検証・引継ぎ記録）を管理する。既存原稿を直す場合は `content.yaml` の `manuscripts.en.file` に記された英語正本を更新し、既存の配置と履歴を尊重する。
4. `content.yaml` のスキーマ・固定値・既存IDとURLは海外向け運用契約に従う。新規原稿は `status: draft`、実施していない `verification.lab` や `independent_review` は `pending`、未公開の媒体は `unpublished` / URLは `null` とし、日付・URL・成果を推測で埋めない。確認した根拠がある状態のみ更新する。
5. Medium再掲載用の手順・管理ファイルが必要な場合は運用契約に従って 同じ作品ディレクトリの `PUBLISHING.md` に日本語で記録する。**英語本文を複製しない**。未公開のSubstack URLやcanonical設定を完了済みと記載しない。
6. 有料企画・既存のPayhip原稿は重複と境界の判断に必要な範囲だけ参照し、内容・コード・未公開ノウハウを無料記事やPRへ転記しない。

## 2. 読者に届ける価値を設計する

執筆前に次を簡潔に整理し、必要な内容だけ本文へ反映する。

- **読者**: Linux管理者、開発者、初心者、一般読者など、誰が何を知っているか。英語を読めることと特定の国・文化・サービスを知っていることを混同しない。
- **中心となる問い**: 検索やAIへの質問以前に、読者が何に疑問を持つべきかを含め、記事が答える一つの問いを特定する。
- **読後の成果**: 仕組みの理解、選択基準、実行できる手順、検証方法、考えるための視点のうち、何を残すか。
- **記事の境界**: 無料記事単独で結論・重要な注意点・最小限の解決まで届ける。網羅的な運用教材や深い実装は有料企画の候補に分離できるが、無料の結論を出し惜しみしない。
- **独自性**: 実体験、失敗、問いの立て方、比較条件、意外な着眼点を確認する。一般論だけを増やさず、体験がないものを一人称の体験談として創作しない。

記事を何文字・何見出しにするかを事前の目標にしない。必要な背景、理由、例、条件を欠かさず説明することを優先する。

## 3. 調査と実機確認

[制作・レビュー手順](../../../docs/article-workflow.md)の一次情報・実測・安全性の方針を適用する。

- 重要な仕様、バージョン、料金、対応状況、セキュリティの効能、比較は一次資料（公式文書、標準、原実装、原著論文等）で確認する。変化し得る事実は確認日・対象バージョン・適用条件を記録する。出典を読んでいない事実を引用・検証済みとして書かない。
- 技術手順が記事の価値なら、可能な範囲で隔離した環境で再現する。OS、ディストリビューションのバージョン、シェル、権限、ホスト／コンテナ、作業場所、前提設定、実行コマンド、期待結果と **実際の結果** を分けて日本語の `REVIEW.md` に記録する。
- SSH、UFW、IPv4/IPv6、クラウドFW、サービス再起動、破壊的コマンド等は、対象環境・接続断の危険・バックアップや復旧経路を **操作の前** に説明する。現在の接続状態やVPSのコンソール可否を推測しない。
- ハンズオンでは準備→設定と理由→実行→成功判定→典型的失敗の診断→復旧・後片付けを、内容に応じて揃える。理解と再現に必要なコードや設定を `...` で省略しない。
- 実行不能な検証を成功例で埋めず、未実施の手順・疑わしい主張は未検証として明記する。重要な未検証が残る場合は公開準備済みと扱わない。課金、秘密情報の公開、破壊的操作、本番環境の変更は勝手に実行しない。
- 解説や思想・エッセイでは実機検証を機械的に強制しない。具体的な歴史・統計・サービス仕様と筆者の見解を区別し、論理が成り立つかを確認する。

## 4. 英語で執筆・再構成する

### 英語圏読者への説明

- 英語として自然な文章構造で書き、単語を置き換えるだけの和文英訳にしない。必要な範囲で段落や例の順序を組み替えるが、根拠・留保・主張の強さは変えない。
- 技術者が使う一般的な英語の専門用語を正確に用いる。正確性を壊す過度の平易化、未定義の略語、曖昧な代名詞を避ける。
- 日本固有の制度・文化・サービス・ネットワーク条件が理解に必要なら説明する。日本発という視点は自然に残し、米国・英国のどちらかに無理に寄せない。英米差や地域制限は結論に影響する場合に具体的に書く。
- タイトルは読者の問題と本文の成果を表し、誇大な安全性、過度な煽り、根拠のない性能保証を避ける。検索向けの語を優先するために記事の正確性・著者の視点を犠牲にしない。

### 人間の文章としての流れ

- 著者の疑問・判断・失敗の経緯・独自の比喩・ユーモアを活かす。エッセイを無理に中立的な教科書に変えず、意見と事実は明確に分ける。
- 意味を増やさない大げさな導入、抽象的なまとめ、同じ結論の反復、紋切り型のつなぎ句を避ける。特定の英語表現を機械的に禁止せず、段落が理解を前進させるかで判断する。
- 因果関係は文章でつなぎ、実行順・比較・確認項目には必要に応じてリストや表を使う。一文ごとの改行・装飾的な小見出し・無意味な太字を乱用しない。
- **短縮は目的にしない**。日本語原稿から英語化するとき、主張の背景、論証、比喩、条件、例外、復旧手順を落とさない。重複だけを整理し、原文の独自性を守る。

### 記事の種類に応じた構成

- **技術Tips**: 読者の問題→適用環境→原因・理由→実行可能な解決→結果確認→必要な例外・復旧。
- **技術解説**: 中心の問いと結論→仕組み→具体例・比較条件→制約と判断基準。実装不要なら無理にコードを入れない。
- **エッセイ・思想**: 著者の問いや観察→論理の展開・具体例→反論や留保→読者に残る考え方。安易な自己啓発調の結論にしない。

上記は型を強制するものではない。原稿の内容に合う構成を優先する。

## 英語正本から作る日本語レビュー用原稿

日本語レビュー版を用意する場合は、[文体プロファイルの「自然な日本語」の基準](../../../docs/author-voice-profile.md)を必ず適用する。英語の文を順番に訳すのではなく、**英語記事が伝える技術的な事実・条件・例外を、日本語で説明し直す**。原文の論旨は保つが、段落順・文の長さ・接続詞・比喩の位置は日本語として自然になるよう変更してよい。

- 「この動きなら〜が気になります」「ここにも注意があります」など、根拠のない心理描写や空疎な前置きを足さない。説明したい現象、理由、手順から直接書く。
- 英文と日本文は単語・文数ではなく、仕様、数値、コマンド、条件、制約、実測の有無が一致するかで照合する。
- 書き上げたら、英語を見ずに日本語稿だけを通読する。日本語の技術記事として引っ掛かる表現が複数あるなら、翻訳の校正で済ませず段落から組み直す。
- 日本語版を作った事実だけで、自然な日本語になったと判断しない。未実施のテストや経験を補って語り口を作ることもしない。

## 5. 既存日本語記事からの英語展開

1. 原文の公開状態・権利関係・関連企画を確認する。原文がなければ日本語記事を存在すると仮定しない。
2. 原文の核となる主張、著者の見解、理由と例、技術的前提、重要な例外を抽出する。英語版で省略・補強する理由がある場合は記録する。
3. 英語圏で意味が伝わらない例だけ、意味の等しい説明や補足を追加する。内容を一般論に置き換えたり、原文と異なる事実を創作しない。
4. 英語版は別の読者へ独立して価値を届ける記事にし、原文を逐語翻訳しただけにしない。原稿間の対応・重複や変更理由は日本語の `REVIEW.md` に残し、本文に編集メモを混ぜない。
5. 無料記事を英語展開する際もPayhip有料原稿への無断転用や未公開教材の流出を避ける。

## 6. 自己レビュー・独立レビューへの引継ぎ

提出前に、原稿の中心的な問い・事実・文章を自分で点検する。

- タイトルが本文の約束を守り、無料記事だけで読後の成果を得られるか。
- 技術情報・実機検証・引用・リンク・図・コマンド・前提条件が整合するか。
- 英語表現は自然で、著者の視点と情報量、根拠・例外条件を保持しているか。
- 英語圏読者に不要な日本固有の前提を要求していないか。
- `content.yaml` の正本・状態・記録と実体が一致し、未実施を確認済みにしていないか。

`REVIEW.md` に日本語で、対象記事と版、読者・問い、編集判断、日本語原稿との関係、参考資料、実機環境・コマンド・結果、未確認項目、自己レビューの結果と独立レビューへの申し送りを記録する。既存の実測欄、指摘ID、公開ブロッカーを削除しない。記事本文は制作メモなしでも理解できる状態にする。

`english-article-review` が利用できる場合は、原稿の独立した公開前レビューを委ねる。未導入なら独立レビューが必要と記録し、自己点検をもって `verification.independent_review` を完了にしない。

## 完了とGit運用

- 指定された記事正本と、その記事の管理・検証記録だけを新規作成・更新し、他媒体に本文を複製しない。
- PR作成を依頼された場合は日本語で目的、変更ファイル、無料記事で完結する問い・成果、有料企画へ残す論点、検証範囲、未確認事項、Draftを維持する条件を記載する。未公開の有料内容は転載しない。
- 下書きの作成・コミット・Draft PRの作成を、公開・販売・独立レビュー完了として扱わない。Substack/Medium投稿、Payhip登録、PRマージは明示的な指示なしに行わない。
- 最終報告では、原稿パス、狙い、主な変更、実測／未検証、独立レビューの必要性を簡潔に示す。

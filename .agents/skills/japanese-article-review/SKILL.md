# 日本語の無料記事レビュー

媒体を問わない日本語の既存無料記事を公開前に **独立して検証する** Skill。執筆時の「確認済み」「動作した」をそのまま信用せず、重要な主張を自分で確認する。原則としてレビュー中は本文を変更しない。

作業前に[共通編集方針](../../../docs/editorial-policy.md)と[制作・レビュー手順](../../../docs/article-workflow.md)を読む。共通の4観点・無料範囲・重大度・判定基準を適用し、下の内容・読者に応じた確認を加える。新規執筆と全面改稿は[japanese-article](../japanese-article/SKILL.md)、有料記事は [japanese-paid-article-review](../japanese-paid-article-review/SKILL.md)、有料書籍は [japanese-paid-book-review](../japanese-paid-book-review/SKILL.md) が担当する。

**著者の声の保全:** [生原稿由来の文体プロファイル](../../../docs/author-voice-profile.md)を参照する。短い語り口や自然な余談だけを理由に修正を強制しない。事実誤認・安全性・必要な説明不足は従来どおり指摘し、個性の抹消と適切な校正を区別する。

## 1. 対象と読者を確定する

1. 指定された Markdown 原稿を読む。対象が曖昧なら、ユーザーが編集中のファイルや依頼文から特定する。
2. 対象の親ディレクトリから `README.md`、`MEMORY.md`、`AGENTS.md` と関連する既存記事を確認する。
3. 想定読者、記事の中心的な問い、読後に得られる成果、シリーズとの関係を一文ずつ整理する。
4. 既存シリーズ固有の `MEMORY.md`（存在する場合のみ） の初心者向け Web 制作シリーズの方針を、無関係な AI・セキュリティ・Symbol 記事へ機械的に適用しない。
5. 他媒体の原稿を元にしていると判断できる場合、利用可能な範囲で元記事との差、対象読者向けの付加価値、重複を確認する。

対象シリーズの方針は該当記事だけに適用する。通常は対象原稿の修正や公開操作を行わない。

## 2. 重要な主張を抽出して検証する

記事を通読し、次を優先順に確認する。

- **結論に直結する主張**: 安全性、危険性、比較、性能、費用、対応状況など。
- **操作の結果**: 実際に実現できると説明した手順、コード、設定、期待される表示。
- **時点に依存する事実**: 製品・サービスの仕様、プライバシーポリシー、利用条件、価格、法制度、リリース状況。
- **読者の行動に影響する記述**: セキュリティ設定、認証・署名・秘密情報の扱い、公開・送金・課金など。
- **引用や参考リンク**: 本文の主張を実際に裏付けているか。リンク先が存在するか。

事実確認は一次情報を優先し、記事に示された出典を独立に読み直す。公式仕様、標準文書、公式ヘルプ、ソースコード、原著論文等から確認する。二次記事だけを根拠に断定しない。

- 仕様として保証されること、環境依存で観測されたこと、将来構想、著者の推測を区別する。
- 「完全」「絶対」「必ず」「乗っ取られない」「安全」など強い断定には根拠と適用条件を求める。
- パスキー、二要素認証、AI へのデータ入力、本人確認、電子署名では、攻撃条件・回復手段・サービス固有仕様等の抜けを確認する。
- Symbol 記事では NEM/NIS1 との混同、署名と取引確定の混同、オンチェーン保証と外部運用の混同を確認する。他チェーンも一次情報で固有仕様を確認し、根拠のない優劣断定や仕様の混同を調べる。
- 有効な情報源へアクセスできない事項は `Unverified` と記録する。確認していない事実を確認済みにしない。

## 3. 実践記事は再現する

コード、CLI、手順が主要な価値を持つ記事では、可能な範囲で実際に追試する。

- 想定 OS、ツールのバージョン、作業ディレクトリ、事前準備が記載されているか。
- 記事のコマンドや Codex への指示文だけで意図した結果に到達できるか。
- 記事の表示例・ログ・エラー・期待結果と追試結果が整合するか。
- 記事が依存するファイルと、シリーズの前回までに作成したファイルが一致するか。
- コードを知らない読者に、未説明のコード入力や暗黙の判断を要求していないか。

追試のために破壊的操作、実資産の送金、秘密情報の公開、サービスの課金を実行しない。安全に再現できない場合は、代替できる範囲まで確認して残りを `Unverified` にする。

## 4. 日本語の読み物としてレビューする

- **タイトルと導入**: 読む理由と扱う問いが明確か。中身とずれた煽り・誇張がないか。
- **答えの位置**: 重要な結論を過度に引き延ばしていないか。前置きが長すぎないか。
- **伝わり方**: 非技術者向けなら身近な例があり、専門用語の初出説明があるか。技術者向けなら曖昧な比喩で正確性を損ねていないか。
- **独自の価値**: 読者が新たに理解できる点・試せること・判断基準が具体的か。検索結果の寄せ集めや一般論だけになっていないか。
- **文章品質**: 重複、空疎な総括、冗長な箇条書き、不要な絵文字、不自然な大げさ表現、誤字や表記揺れがないか。
- **実用性**: 実践記事なら結果確認と失敗時の確認点まであるか。解説記事なら例外や制限が説明されているか。
- **形式**: 正本と掲載稿の役割に合った形式か。[掲載形式](../../../docs/japanese-publication-formats.md)を参照し、既存ID・slug・公開設定を保持しているか。
- **シリーズ整合**: 過去記事との説明・操作のつながりがあり、同じ説明の反復が過剰でないか。
- **無料記事の範囲**: 一つの問いに完結し、結論や重要な注意点を隠していないか。有料相当の深い実装・網羅的検証に広がったり、既存の有料原稿・コードを流用したりしていないか。

「売れそう」「バズりそう」など根拠のない予測は判定理由にしない。好みだけの修正は Minor または任意提案とする。

### 説明が長く、目が滑る文章になっていないか

[japanese-article の読みやすさの編集方針](../japanese-article/SKILL.md)に対応して、次を確認する。

- **説明の重複**: 定義・言い換え・たとえ・再説明が同じ内容を繰り返していないか。各段落が理解を進める情報を加えているか。
- **前置きと結末**: 「〜と思うかもしれません」や「大切な仕組みです」を重ね、本題を遅らせていないか。結末は要約や抽象的な励ましの反復ではなく、読者が取れる行動や判断基準につながるか。
- **説明の流れと見出し**: 仕組みと、それによって起こる問題を一続きで追えるか。同じ場面の対策が細かな見出しに分散していないか。一文ごとの改行や短い断片の連続が、流れを妨げていないか。
- **箇条書きの用途**: つながりを説明する部分は段落で読めるか。復旧手順や確認項目は、実行しながら見比べやすい形になっているか。
- **短縮で失われた意味**: 結論を変える条件・例外、対策の限界、必要な操作が省かれていないか。例えばCookieの再利用条件や、パスキーでも防げない攻撃が抜け、安全性を過大評価させていないか。改稿前の原稿や差分が利用できれば比較する。

文字数・短縮率・見出しの数だけで良否を決めない。指摘では対象の文や段落を示し、何が重複するか、どこで理解が途切れるか、最小限の削除・統合案を説明する。局所的な冗長さは通常 Minor とし、Major は中心的な内容を理解・実行できない場合や、重要な条件の欠落で誤解を生む場合に限る。

## Learnings

### 初級読者の理解と操作を照合する

[執筆側の具体的な編集方針](../japanese-article/SKILL.md#learnings)に対応し、技術的な正しさとは別に次を確認する。

- **説明が始まる前の前提**: 製品名・設定キー・値・形式名が突然現れず、想定読者がその意味と役割を本文だけで追えるか。見出しの対象、「両方」「同じ」といった指示先、同値とする範囲・条件が明確か。例えば「ヘルスチェックがないから同じなのか」という疑問が残る説明は、仕様を確認して必要な条件を補う。
- **設定例と比較操作**: 説明するコマンドの設定内の位置が分かるか。比較で変更する箇所と保持する箇所が明確で、初級読者が設定全体を推測して組み立てなくてよいか。処理順を追えるかも確認する。全量掲載や番号付きリストを一律に要求せず、読者が理解・実行できない箇所に絞って提案する。
- **結果の証拠**: 成功条件が、具体的なコマンド・状態表示・ログに対応しているか。設定検証と動作確認、状態表示と処理結果、初回起動と起動後の再実行を取り違えていないか。確認先が曖昧なだけなら局所的な説明不足として扱い、結論の根拠自体が欠ける場合は重大度を分けて判断する。
- **補足の必要性と文体**: 補足や再実行手順が中心の問いへの回答を助けているか、かえって検証目的を曖昧にしていないか。条件・限界を落とさず整理できる箇所と、理解に必要な説明不足を区別する。語尾や接続句は段落の流れで判断し、好みの言い回しへの統一を必須修正にしない。

## 5. 重大度と公開判定

- **Critical**: 読者の資産・アカウント・秘密情報・安全に重大な危害を及ぼし得る誤案内。危険な送金や認証操作、漏えいを誘発する内容。
- **Major**: 結論を左右する事実誤認、重要な根拠不足、主要手順の再現不能、想定読者が中心的な内容を理解・実行できない構成、誤解を生む強い断定。
- **Minor**: 誤字、局所的な説明不足、冗長さ、段落や見出しの改善、中心結論に影響しない表現。

**PASS**: Critical / Major がなく、結論を支える重要な主張に公開を妨げる未検証がない。Minor が残っていてもよい。

**REVISE**: Critical または Major が1件以上ある。記事の核心となる主張や主要手順を確かめられず、正確性が判断できない場合も REVISE とする。

「改善するともっとよい」だけで Major にしない。現実に読者へ与える影響で重大度を決める。

## 6. レビュー結果の形式

通常は本文を変更せず、対象箇所、問題、影響、根拠、最小修正案が分かる形で返す。

```markdown
# Review Result

判定: REVISE
対象: contents/free/draft/記事の日本語タイトル/article.ja.md
想定読者・記事の目的: ...

## Critical
- [NR-001] 対象箇所（見出し・行・引用）
  - 問題:
  - 読者への影響:
  - 根拠:
  - 修正案:

## Major
- [NR-002] ...

## Minor
- [NR-003] ...

## Verified
- 確認した一次資料と対応する主張
- 再現した環境・コマンド・結果（実施した場合）

## Unverified
- 未確認事項、理由、判定への影響
```

PASS の場合も冒頭の判定と対象を残す。空セクションは省略可。各指摘には `NR-001` から連番を付け、再レビューでは同一問題の ID を維持する。

読みやすさの確認結果も、問題があれば指摘として、問題がなければ短い所見として示す。事実確認の `Verified` と混同せず、文章の流れや重複について何を確認したかを具体的に書く。

## 7. 修正依頼・再レビュー

- 「指摘を直して」など明示的な依頼があったときだけ記事本文を変更する。
- 必要な箇所だけ変更し、元の読者と文章の方向性を保つ。重要な意味が変わる修正は根拠や再現結果を再確認する。
- 再レビューでは前回指摘の解消状態を追跡し、新しい問題を導入していないかを調べる。
- レビュー報告は応答で返し、記事本文へ挿入しない。対象の版、確認日・方法・範囲、根拠、判定、未検証事項は対象作品と同じディレクトリの `REVIEW.md` に記録する。公開操作は行わない。

## 技術記事と掲載稿の追加確認

OS、バージョン、シェル、作業場所、権限、ホスト／コンテナ、置換する値を区別し、主要手順を可能な範囲で追試する。問題例と修正版、成功判定、失敗時の診断、後片付け、破壊的操作前の影響説明を確認する。表示未確認の図や記法は確認済みにしない。

Node.js・TypeScriptを扱う場合は、実行時と型検査・変換、ESM/CommonJS、npm/pnpm、OS固有の挙動を区別する。既存の媒体別レビュー指摘IDと記録を保持し、新規記録は作品内の `REVIEW.md` に置く。既存掲載稿に付随するメモは自動移動しない。

# 日本語の無料記事制作

掲載媒体を問わない日本語無料記事の執筆 Skill。読者に「読んで分かった」「試してみたい」「判断できる」という具体的な価値を残す。内容のない水増し、過剰な煽り、AIらしい定型的な美辞麗句を避ける。

作業前に[共通編集方針](../../../docs/editorial-policy.md)と[制作・レビュー手順](../../../docs/article-workflow.md)を読む。独立した公開前検証は[japanese-article-review](../japanese-article-review/SKILL.md)、有料記事の制作は[japanese-paid-article](../japanese-paid-article/SKILL.md)に任せる。

著者らしい語りは[生原稿由来の文体プロファイル](../../../docs/author-voice-profile.md)を参照する。問いから入る自然さ、本人の発見・判断・控えめな余談を残し、定型的な説明文に均質化しない。ただし一般読者に必要な前提と正確性を優先する。

## 対象とルーティング

- 「日本語で記事を書いて」「記事にして」「下書きを作成」「過去記事を再構成」「記事を改稿」などの依頼で使用する。
- 単なる記事の公開前採点や独立した事実確認だけならレビュー Skill を使う。
- 対象ファイルが指定されていればそれを優先する。指定がなく、このリポジトリで日本語無料原稿を新規作成するなら `contents/free/draft/<日本語記事タイトル>/article.ja.md` と同階層の `content.yaml` に保存する。
- 最初に `contents/AGENTS.md` と対象に関係する `MEMORY.md` / `AGENTS.md`、既存記事を読む。必要ならルート README と関連媒体の原稿も確認する。
- 既存シリーズ固有の `MEMORY.md`（ある場合のみ） の初心者向け Web ページ制作方針は **そのシリーズに適用する方針** であり、セキュリティや Symbol などすべての 日本語記事に一律適用しない。シリーズの場合は前後の記事を読み、操作や用語を引き継ぐ。
- ユーザーがテーマを示しているなら、明白な不明点がない限り執筆に進む。読者レベルはテーマ、依頼文、既存シリーズから判断する。

## 執筆の手順

### 1. 記事の価値を決める

本文を書く前に内部で次の3点を一文ずつ整理する。

1. **対象読者**: 何に疑問を持つ人か。技術者・非技術者を最初から混同しない。
2. **一つの中心的な問い**: この記事で何が分かるのか。話題を広げすぎない。
3. **読後の成果**: 判断基準、理解、実際の操作、検証結果のどれを持ち帰れるか。

専門用語が主題であっても、題名と導入は読者が抱く疑問から入る。単なる用語集や製品宣伝にしない。実体験や検証が存在しないのに体験談として書かない。

### 2. 先に事実を確かめる

- 重要な事実・数値・比較・制度・セキュリティ上の効能は一次情報を優先する。公式仕様、公式ドキュメント、標準文書、原著論文、公開実装を確認する。
- 時期によって変化する話題（AIサービスのデータ取扱い、パスキー対応状況、料金、UI、脆弱性、制度等）は公開時点に近い情報を確認し、必要なら確認日・対象バージョンを書く。
- 検索や資料確認ができない場合は事実を創作しない。重要な未検証事項は断定を避け、本文または作業報告で明示する。
- 規格上の性質、実装・設定による違い、個別サービスの運用、著者の見解を分ける。例えば「安全性が高い」を「絶対に乗っ取られない」に変えない。
- 情報源の URL は実際に確認したものだけ載せる。参考リンクは本文中の該当主張付近または末尾の短い参考資料に置く。架空の出典を作らない。
- Symbol を扱う場合、Symbol と NEM/NIS1、プロトコル・SDK・REST、署名・承認・確定、Mainnet・Testnet を区別する。他チェーンについても対象プロトコルの一次情報を確認し、仕様を流用しない。

### 3. 記事の種類に合わせて構成する

**一般向けの解説・セキュリティ・AIの記事**

- 冒頭で読者の疑問と暫定的な答えを提示し、何が分かる記事かを早めに示す。
- 身近な具体例から入り、必要な専門用語だけ初出で短く説明する。
- メリットだけでなく、前提条件・できないこと・例外やリスクを示す。
- 結末は抽象的な感想ではなく、読者が取れる行動または判断基準で締める。

**手順・ハンズオンの記事**

- 想定環境、準備するもの、完成状態、手順、結果の確認方法、失敗時の確認点を示す。
- コピー用の指示文・コマンドはそのまま使える形にする。コマンドの作業ディレクトリを省略しない。
- 実行例がある場合は可能な範囲で実際に試す。実行していない出力を実測結果として書かない。
- 初心者向け Web 制作シリーズでは 既存シリーズ固有の `MEMORY.md`（ある場合のみ） を優先し、読者にコードの手入力を要求しない。

**Symbol の活用・アイデア紹介記事**

- 実現済みの機能、設計案、試作、構想を明確に分ける。
- オンチェーンで保証されることと外部サーバー・運用に依存することを混同しない。
- できることだけでなく、実現に必要な前提、制約、費用や安全上の考慮を必要な範囲で説明する。

### 4. 日本語記事として編集する

- タイトルは内容を正しく伝える。検索される言葉や素朴な疑問形は使えるが、煽りや断言のしすぎは避ける。
- 冒頭は短く、本題までに長い一般論や自己紹介を挟まない。
- 見出しは意味のある単位で付ける。1段落や1文ごとに小見出しを増やさない。
- 日本語は平易かつ正確に。一文を長くしすぎず、箇条書きの乱用を避ける。不要な絵文字、過剰な太字、定型的な「いかがでしたか」は使わない。
- 文字数を固定しない。伝える価値を満たしたところで終える。専門的な核心を短縮しすぎない。
- 正本は通常のMarkdownで、原則 `# タイトル` から始める。掲載用の形式は必要な媒体だけ[掲載形式](../../../docs/japanese-publication-formats.md)を参照する。
- 単独記事は単独で理解できるようにする。シリーズ記事は過去記事への依存を最小限にして、前回との接続を短く説明する。

#### 説明が長く、目が滑る文章を整える

- 同じ内容を「定義→言い換え→たとえ→再説明」と繰り返さない。具体例やたとえで伝わった部分の再説明は削り、次の疑問へ進む。
- 「ここまで読むと〜と思うかもしれません」「大切な仕組みです」といった前置きや評価を重ねず、何が起きるか、なぜ起きるかを具体的に書く。結末も本文の要約や抽象的な励ましを重ねず、読者が最初に取れる行動で終える。
- 仕組みと、その仕組みで起こる問題は、一続きで読めるようにする。細かく分けた対策は、読者が同じ場面で行うものをまとめる。見出しや対策の数を固定しない。
- 説明は段落でつなぎ、復旧手順や確認項目など、見比べながら実行する部分には箇条書きを使う。一文ごとの改行や短い断片の連続で、流れを途切れさせない。
- 短くするときも、結論を変える条件・例外、対策の限界、復旧に必要な操作は残す。例えば「盗んだCookieが必ず使えるわけではない」「パスキーでもログイン後の情報窃取は防げない」を、読みやすさのために削らない。補足用語は理解に必要な場所へ置き、主筋を妨げるなら末尾の注記に移す。
- 削減率や文字数を目標にせず、読者が仕組みと行動を追えるかで判断する。改稿後は元原稿と比べ、重複を削った結果、根拠・条件・操作の意味まで変わっていないか確認する。

### 5. 無料記事の範囲と制作記録

- 一般読者向けに一つの問いを短めに解く。必要な結論・条件・注意点は残し、長大な完全ハンズオンや深い実装・網羅的検証は有料企画へ分ける。文字数やコード量だけで境界を決めない。
- 他媒体から再構成する場合は元記事を確認し、対象読者の疑問と成果に合わせる。既存の有料記事・本の内容やコードを無料下書きへ流用・先行公開しない。
- 有料版への不自然な誘導や注意点の隠蔽を避ける。価格・公開日等が未定なら予告しない。有料企画の執筆を無料記事の依頼に自動追加しない。
- 原稿と分けて対象作品と同じディレクトリの `REVIEW.md` に対象・問い、編集判断、検証、レビュー、未検証事項を記録する。公開本文はメモなしで読めるようにする。
- PR作成を依頼された場合は、共通編集方針の「無料記事としての範囲」「有料企画に残す発展論点（あれば）」を本文に明記する。

## Learnings

### 初級読者が説明と設定例を行き来できるようにする

- **導入と見出し**: 一般的な問題から特定の製品の例へ移るときは、「今回はDBにPostgreSQLを使う」のように関係を示してから製品固有の説明へ進む。見出しは「短い形式」のような未説明の分類名より、「depends_onにサービス名を指定するだけでは起動順しか待たない」のように対象と動作を示し、導入で伝えた製品名を見出しで繰り返すだけにしない。
- **用語と設定の意味**: 初級者を含む記事では、設定キーや値を挙げるだけでなく、何を指定し、どんな動作になるかを初出で説明する。理解・実行に必要な説明を公式資料へのリンクだけで代替しない。「両方が必要」「同じ意味」と書くときは対象を明示し、同じになる範囲や条件を示す。例えばサービス名だけのdepends_onとservice_startedは、ヘルスチェックの有無に関係なく同じ待機条件であると説明する。
- **コードとの対応**: 読者が設定をコピーして試す場合も、説明中のコマンドがどこにあるか分かるようにする。例えば「ヘルスチェックのコマンド」だけでなく「dbのhealthcheck.testにあるpg_isready」と示す。起動順や処理順が主題なら、誰が何を待って次へ進むかを番号付きリストなどで追えるようにする。
- **比較例**: 「元の書き方に戻す」だけで済ませず、変更する箇所と残す設定を明示する。初級読者が差分だけでは設定を組み立てにくい場合や、全体の提示を求められた場合は、省略のない最小構成を載せる。例えばhealthcheckを残してdepends_onだけを変える比較では、チェックの実行と成功待機を区別し、作業場所・データの初期条件・後片付けもそろえる。
- **目的と確認先**: オプションの列挙より先に、それを使う目的を示す。成功の条件は「確認できます」だけで済ませず、どのコマンドのどの表示・ログで判断するかまで書く。例えばコンテナの状態と終了コードはps、SQLの結果はlogsで確認する、と対応させる。起動後の再実行が成功しても、初回起動で準備完了を待てた証拠にはしない。
- **補足と文のつながり**: 正確な説明でも、記事の問いへの理解や操作に寄与しない内部仕様・再実行手順は増やさない。必要な条件や安全上の注意は残し、「失敗を見落とさないために、この指定を付ける」のように目的と操作をつなぐ。同じ語尾の連続や後付けの総括を整え、個別のフィードバックで採用した接続句を全記事の定型句にしない。

## 完成時の確認

- 冒頭の問いに本文が答えているか。読者に残る具体的価値があるか。
- 根拠と結論の強さが釣り合っているか。例外や未検証を隠していないか。
- 内容の重複、冗長な導入、架空の体験談、不要な専門用語がないか。
- コード・コマンド・リンク・画像参照を掲載している場合、確認した範囲が明確か。
- 既存記事と矛盾しないか。保存先とファイル名が記事内容に合っているか。

## 最終出力

指定された Markdown 原稿を作成・更新し、変更ファイル、記事の狙い、主要な確認事項、残る未検証点だけを簡潔に報告する。調査メモやレビュー記録は原稿本文へ混ぜない。自動公開はしない。

## 英語版への引き渡し

英語化も依頼された場合は、日本語稿を翻訳元として[制作経路](../article-workflow/SKILL.md)に従う。無料記事の英語版には `english-article` を使い、文体プロファイルと著者の視点を引き継ぐ。

## 実践・技術解説の補足

Ubuntu・Docker・CLI等の手順はOS・シェル・作業場所・権限・ホストとコンテナを区別し、準備、操作と理由、成功の確認、失敗時の診断、必要な後片付けまで示す。最小構成を実行し、未実行の結果を成功例にしない。技術解説は一つの問いに答え、シリーズの入口でも結論を先送りしない。解説やエッセイに不要な実装を強制しない。

掲載稿の作成時は[掲載形式](../../../docs/japanese-publication-formats.md)を読み、掲載先だけで読者像や記事構成を固定しない。

掲載稿の雛形は各媒体の導入済みCLIから生成し、独自のテンプレートを保守しない。正本や他媒体へfront matterを持ち込まない。

日本語正本の制作は本スキルが担当する。自然な英語への翻訳と英語読者向けの調整は対応する英語側スキルの責務とし、本スキルに翻訳処理を重複して持たせない。

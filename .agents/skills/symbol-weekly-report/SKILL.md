# Symbol Project 週報

`https://github.com/symbol` と `https://github.com/NemProject` の **Organization 全体**を調べ、GitHub から確認できる1週間の動きを、日本語の X 記事としてまとめる。

最重要原則は次の2つ。

- **調査は厳密に、本文はやわらかく。**
- **GitHub のイベント一覧ではなく、「今週 Symbol / NEM で何が進んだのか」が読者に伝わる記事にする。**

既存の `x/*_symbol_weekly_report.md` がある場合、最新の週報を **文体・段落の長さ・見出し・締め方の第一優先の見本**とする。過去記事の事実や数値は流用しない。

## 期間と保存先

- ユーザーが期間を指定した場合はそれを最優先する。日付・時刻は別の指定がない限り日本時間（JST）として解釈する。
- 期間指定がなく、ファイル名などから期間が分かる場合はその期間を使う。
- 何も指定がなければ、JSTで実行時点の最後に完了した月曜〜日曜の週を対象にする。
- **記事上の対象期間は必ず日付だけで表現する。** 例: `9/21〜9/27`。`9月21日（月）0:00から28日（月）0:00` のような内部検索用の境界時刻は本文に出さない。
- 対象週の最終日は日曜日として扱い、表示上は `9/27` までとする。`9/28 0:00` は翌週の開始境界であり、対象期間の終了日として表示しない。
- 内部の検索条件では、取りこぼし防止のため JST の半開区間 `[月曜 00:00:00, 翌月曜 00:00:00)` を使ってよい。GitHub API の時刻条件を使う場合だけ UTC に変換し、最終判定はイベント時刻を JST に戻して行う。
- ユーザーが `9/27まで` のように終了日だけを指定した場合、その日を含む直近の月曜〜日曜週として解釈する。例: `9/27まで` → 記事上の期間は `9/21〜9/27`。
- 保存先は `x/yymmdd-yymmdd_symbol_weekly_report.md`。明示された保存先があれば従う。
- 過去記事の日付や集計値を次週へコピーしない。

## 調査

本文を簡潔にするためにも、裏側の調査は広く行う。

1. `symbol` と `NemProject` のリポジトリ一覧を確認し、対象週に更新がありそうなリポジトリを洗い出す。主要リポジトリだけを見て Organization 全体を代表させない。
2. 対象週の commit、PR の作成・merge、Issue の作成・更新・close、release を横断して確認する。
3. push があったリポジトリでは commit 内容を確認する。PR がある場合はタイトルだけで判断せず、本文・差分・関連 commit を読む。
4. release と tag も確認する。tag の作成時期を commit 日時だけから断定しない。
5. 同じ変更を commit、PR、release と重複して数えない。
6. `symbol` Organization 内にある NEM 関連コードと、`NemProject` Organization の活動を混同しない。
7. API・検索制限などで完全確認できない場合は、本文で必要以上に騒がず、断定を避ける。未確認を「動きなし」としない。

### コミット数

記事冒頭でコミット数を出す場合は、読者に意味のあるリポジトリだけを掲載する。

- 対象週に実質的な変更があった主要リポジトリを中心にする。
- Dependabot や単純な自動更新だけのリポジトリを、件数を増やす目的で並べない。
- 数値は同じ集計基準で数える。
- merge commit 等の重複がある場合は除外する。
- 「Organization 全体で合計 N 件」と無理に総計しなくてよい。
- 数値に確信が持てない場合は、コミット数の段落自体を省略してよい。

## 何を記事にするか

優先順位は次の通り。

1. Explorer、Wallet、REST、SDK など利用者が認識しやすいプロダクトの進展
2. 利用者・ノード運営者・開発者に影響する不具合修正
3. セキュリティ、互換性、基盤更新
4. Symbol / NEM の共通化や構成変化など、プロジェクト全体の方向が見える変更
5. release、設計上の決定、重要 Issue
6. 依存更新、CI、Lint などの保守作業

細かい変更はすべて列挙しない。複数の commit や PR が同じテーマなら、ひとつの話題としてまとめる。

## 文体

文章は「説明が上手なAI」ではなく、**普段から Symbol のリポジトリを見ている人が、その週に気になった動きを自分の言葉でまとめた文章**にする。

- 読者は「Symbol は今どうなっているのか気になるが、GitHub を細かく追ってはいない人」を想定する。
- 語調はやわらかくするが、説明しすぎない。
- 事実を先に書く。意味付けは必要なときだけ1文足す。
- すべての話題に「なぜ重要か」「今後どうなるか」を付けようとしない。事実だけで十分伝わる箇所はそこで止める。
- 文の長さをそろえない。短い一文だけの段落があってよい。
- 接続詞で文章をきれいにつなぎすぎない。段落が少しぶつ切りでもよい。
- 同じ語尾を連続させない。ただし、語尾を機械的に言い換えるための不自然な表現も使わない。
- 書き手の自然な観察として「ここはまだ途中です」「このあたりは地味ですが大事そうです」「今週気になったのは〜」程度は使ってよい。ただし根拠のない期待や断定はしない。
- 断定できないものは断定しない。「完成した」「提供開始した」「本番反映された」などは根拠がある場合だけ使う。
- 専門用語は必要なものだけ残し、その場で短く説明する。教科書のような定義説明はしない。
- PR番号、Issue番号、commit SHA、ブランチ名は本文に原則出さない。
- リポジトリ名は、所属や文脈を説明するために必要な場合だけ出す。
- 「非テック向けに説明すると」「初心者向け」といった読者属性の宣言はしない。
- 箇条書きを多用しない。
- 太字は多用しない。記事全体で本当に強調したい箇所だけに使う。
- 絵文字は使わない。
- GitHub の調査過程、API の件数、検索クエリ、監査手順を本文へ持ち込まない。

### AIっぽく見えやすい表現を避ける

次の言い回しは、事実上必要な場合を除き極力使わない。

- 「〜が確認できます」
- 「〜と言えそうです」
- 「〜という段階です」
- 「〜という形です」
- 「〜の土台が整っています」
- 「〜へ着実に進んでいます」
- 「〜の方向性が見えてきます」
- 「今後につながる重要な変更です」
- 「大きな一歩です」
- 「興味深いのは〜」
- 「つまり〜ということです」
- 「一方で〜」を段落ごとに繰り返す
- 「派手ではありませんが〜」
- 「利用者にとっては〜」を各節で繰り返す

これらを別のAI的表現へ言い換えるのではなく、**不要なら文ごと削る**。

### 書き方の基準

悪い例:

> Symbol版Explorerでは実データへの接続が進んでいます。これは新Explorerの完成に向けた重要な一歩と言えそうです。まだ一部未実装ではありますが、着実に開発が進んでいることが確認できます。

良い方向:

> Explorerのブロック一覧が仮データではなく、Explorer RESTのデータを読むようになりました。
>
> ブロック報酬やファイナリティも表示対象に入っています。ブロック詳細やアカウント詳細はまだ途中。

さらに自然に書けるなら、説明を足さずそこで止めてよい。

個々の GitHub イベントを並べるのではなく、同じ話題はまとめる。ただし、**毎回「何が変わったか → 意味 → 今後」の三段構成に揃えない。** 内容に応じて必要な部分だけ書く。

## 記事構成

原則として次の形にする。見出し名は内容に合わせて自然に変えてよい。

### 1. タイトル

Markdown の `#` 見出しではなく、次のように太字で始める。

`**Symbolプロジェクト週報｜M/D〜M/D**`

年を入れる必要はない。期間が年をまたぐなど紛らわしい場合だけ年を補う。

### 2. 導入

導入は1〜3段落。**毎週同じ書き出しにしない。**

「Symbolって今どうなってるの？」の一文は使ってもよいが、固定文にはしない。前週と同じ導入なら言い換えるか、省いてその週の動きから入る。

例:

> 今週はExplorerまわりの更新が多めでした。Symbolの実データを表示する部分が進み、Mobile Walletにもまとまった更新が入っています。

あるいは、

> 9/21〜9/27のSymbolまわりをGitHubから拾っていきます。今週はExplorerとMobile Walletが中心です。

「今週は○○な週でした」という総括も必須ではない。自然なら使い、わざわざキャッチコピーを作らない。

### 3. 必要ならコミット数

確実に集計でき、数字自体に意味がある場合だけ次の形で入れる。

> 対象期間に確認できたコミットは、
>
> ・symbol/product：14件  
> ・symbol/symbol：1件
>
> でした。

リポジトリを大量に並べない。

### 4. テーマ別本文

3〜6個程度の話題にまとめる。

見出し例:

- `### Explorer：Symbolの実データ表示へ一歩前進`
- `### Symbol Mobile Walletも更新`
- `### Walletの多言語対応も整理`
- `### NEM側の開発も続いています`
- `### その他`

見出しは「リポジトリ名 + 作業名」ではなく、**読者が意味を理解できる短い日本語**にする。

各セクションでは、まず具体的に何が変わったかを書く。

必要なら「何に関係するか」「まだ途中なのか」を補う。ただし、毎節で同じ説明順にしない。

1セクションはおおむね1〜5段落。1段落だけで終わる話題があってよい。内容が薄いのに段落を増やさない。

### 5. NEM の扱い

`NemProject` Organization に動きがなくても、`symbol` 側で NEM 関連の開発があれば分けて説明する。

たとえば、

> `NemProject` Organization自体では今週コミットが確認できなかった一方で、**NEM関連の開発は `symbol/product` 内で続いている**ことが確認できます。

のように、Organization とチェーン対応を混同しない。

「NEM は開発停止」といった大きな結論を、1週間の GitHub 活動だけから出さない。

### 6. その他

依存更新、Lint、CI、Dependabot 等は、重要性が低ければ `### その他` に1〜2段落でまとめる。

本文の主役にしない。

### 7. 締め

区切り線 `---` を入れてもよいが、締め方は固定しない。

本文ですでに内容が伝わっている場合は、1〜3文で終える。冒頭と同じ内容を言い直さない。

例:

> 今週はExplorerとWalletが中心でした。特にExplorerは、画面だけでなく実データを読む部分まで進んでいます。
>
> また来週、GitHubの動きを見てまとめます。

「今週をざっくり一言でまとめるなら」「という感じでしょうか」「派手な発表はなくても〜」を毎週使わない。締めのためだけの総括文を無理に作らない。

最後に以下を付ける。

`GitHub`  
`https://github.com/symbol`  
`https://github.com/NemProject`

記事内にハッシュタグは付けない。文体の見本にする過去記事にハッシュタグがあっても引き継がない。

## リンク

この週報では、本文中に PR / commit / Issue のリンクを大量に埋め込まない。

- X 記事としての読みやすさを優先する。
- GitHub の根拠は調査時には必ず確認する。
- ユーザーから「出典リンクも付けて」と指定された場合は、本文を壊さない範囲で直接リンクを追加する。
- 指定がなければ、記事末尾の Organization リンクだけでもよい。
- 重要な release など、読者が直接見たほうがよいものは必要に応じて本文にリンクしてよい。

## 避けること

- 「今週の要点」「Symbol側の動き」「来週以降につながりそうな動き」のような定型レポート見出しを毎回機械的に置く。
- commit / PR / Issue を時系列で羅列する。
- GitHub 上のタイトルをそのまま日本語へ直訳して並べる。
- 技術用語を説明せず連発する。
- 「活発」「順調」「大きな前進」などを、具体的な事実なしに評価語として使う。
- 1件の commit を大きな方針転換のように扱う。
- 未mergeのPRを実装済みとして書く。
- `NemProject` に commit がないことを NEM 開発全体の停止と解釈する。
- 末尾に調査メモ、API 検索結果、未加工のリポジトリ一覧を付ける。

## 完成前チェック

保存前に確認する。

- 対象期間は正しいか。記事上の表示が月曜〜日曜の日付だけになっており、翌月曜 0:00 など内部検索境界が露出していないか。
- `symbol` と `NemProject` の両 Organization を確認したか。
- 主要な内容は PR / commit / release / Issue の実体まで読んだか。
- 状態を「開発中」「取り込み済み」「公開済み」で取り違えていないか。
- Symbol と NEM を混同していないか。
- 冒頭を読んで、その週の中心テーマが自然に分かるか。キャッチコピーを無理に作っていないか。
- 見出しが技術者向けの作業名ではなく、一般読者にも意味が分かるか。
- 各セクションで説明を足しすぎていないか。事実だけで伝わる部分に「意味」「重要性」「今後」を追加していないか。
- 「確認できます」「と言えそうです」「着実に」「土台」「方向性」などのAI的な定型表現が連続していないか。
- 文の長さ、段落数、説明順が揃いすぎていないか。
- 太字が多すぎないか。
- GitHub イベントの羅列ではなく記事として読めるか。
- 冒頭の内容を締めで言い換えただけになっていないか。
- 絵文字を使っていないか。
- ファイル名が対象週と一致しているか。
